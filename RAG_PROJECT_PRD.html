1. Overview & Problem Statement

What This Project Is

A Retrieval-Augmented Generation (RAG) system that lets a user upload documents (starting with your own 4 project READMEs) and ask questions about them in plain English. The system finds the most relevant piece of the document and uses it to generate an accurate, grounded answer — instead of guessing from general knowledge.

The Problem It Solves

A general-purpose LLM (ChatGPT, Groq, Gemini) doesn't know your private documents — it can only answer from what it memorized during training. If you ask it something specific to your own files, it either says "I don't know" or, worse, confidently makes something up (a "hallucination"). RAG solves this by handing the model the *actual relevant text* before it answers, the same way an open-book exam works better than a closed-book one.

Why This Project, Why Now

This is your first project that isn't classification/prediction — it's a retrieval + generation system, the architecture behind the most in-demand AI product category right now (document Q&A, internal knowledge assistants, chatbots over private data). It directly closes a gap that already cost you one job application (a role requiring production RAG experience).

3. Complete System Map & Pipeline (Detailed)

This section maps every single step the system takes, split into two separate flows: Flow A — Setting up the knowledge base (happens once per document, when it's uploaded) and Flow B — Answering a question (happens every time a user asks something). These are separate pipelines that share the same storage layer in the middle.

Why Two Separate Flows Matter

Flow A (ingestion) is slow but rare — it happens once per document, so it's fine if it takes a few seconds per file. Flow B (answering) is fast and frequent — it needs to feel instant every time someone asks a question. Understanding this split is exactly the kind of system-design insight that separates "I followed a tutorial" from "I understand why RAG is architected this way."

8. Build Phases & Milestones

Phase 1 — Document Ingestion (~1 weekend)
Upload a PDF, extract text with PyMuPDF. No AI yet — just confirm you can reliably get clean text out of a real document.
Phase 2 — Chunking (~1 weekend)
Write your own manual chunking function first. Test it on your project READMEs, inspect the output chunks by eye to confirm they make sense.
Phase 3 — Embeddings (~1 weekend)
Load all-MiniLM-L6-v2, embed your chunks, print/inspect the vectors. Confirm similar-meaning chunks produce similar-looking vectors.
Phase 4 — Chroma Integration (~1-2 weekends)
Store your embedded chunks in Chroma. Learn its query API. Confirm it returns sensible results for a test question.
Phase 5 — LLM Generation (~1 weekend)
Connect retrieved chunks + question to Groq. Confirm the model answers using only the provided context, not outside knowledge.
Phase 6 — Frontend + Deployment (~1-2 weekends, budget extra time)
Build the upload + chat UI, wrap it in FastAPI, deploy via Docker to Render.com (not HF Spaces — see below), connect Cloudflare DNS, wire up GitHub Actions CI/CD.

Deployment Steps — Learned From the Urdu Sentiment Migration

  1. Create the Render Web Service — connect your GitHub repo, select Docker as the environment, Render auto-detects your Dockerfile
  2. Watch RAM usage from day one — Render's free tier caps at 512MB RAM. Your last project hit OOM crashes (Exit 137) here. This project's footprint should be much lighter than dual XLM-RoBERTa models (all-MiniLM-L6-v2 is ~90MB vs. 2.2GB), but don't assume — monitor actual boot memory
  3. Use CPU-only PyTorch/dependency wheels if size becomes an issue — if any dependency pulls GPU binaries by default, add --extra-index-url https://download.pytorch.org/whl/cpu to requirements.txt, same fix that cut a previous project's footprint from 3.5GB to 150MB
  4. Consider lazy loading if boot is slow — load the embedding model only when the first request comes in, not at container startup, if cold-start memory spikes cause issues (this fixed a previous 2.2GB startup spike down to 35MB boot footprint)
  5. Set up Cloudflare DNS once Render confirms the service is live — add the custom domain, watch for the "DNS record managed by Workers already exists" conflict if any old Worker routes exist from other projects; delete conflicting Workers first
  6. Toggle Cloudflare proxy to DNS Only during domain verification — Render's verification scanner fails if Cloudflare's orange-cloud proxy masks the origin CNAME. Switch to grey-cloud (DNS Only) to verify, then switch back to orange-cloud (Proxied) afterward for CDN/SSL benefits
Total realistic timeline: 6-8 weekends for the core build, plus extra buffer on deployment specifically (Phase 6) given the real friction encountered last time — better to expect 1-2 weekends for deployment alone, not treat it as a quick final step.

9. Risks & Assumptions

Risk — Chunking quality is invisible until tested. Bad chunk boundaries (cutting mid-sentence, too large/small) silently hurt retrieval quality without throwing any errors. Mitigation: manually inspect chunk output by eye during Phase 2 before moving forward.
Risk — Chroma learning curve. First time using a real vector database — expect some setup friction. Mitigation: budget the full "1-2 weekends" for Phase 4, not just 1.
Risk — LLM ignoring provided context. Groq's model might answer from its own general knowledge instead of strictly using retrieved chunks. Mitigation: use an explicit system prompt instruction ("answer only using the provided context; say 'I don't know' if the answer isn't in it") and test this specifically.
Risk — Free-tier platform limits are stricter than they first appear. Modal's free credits ran out mid-use; Hugging Face's personal-account compute is capped at 1 active Space. Mitigation: this PRD already accounts for that by planning Render.com from the start instead of discovering the limit mid-project again.
Assumption: Starting scope is single-document, English-language PDFs. Multi-document support and Roman Urdu are explicitly deferred to v2 (see Future Scope) to keep v1 achievable.
